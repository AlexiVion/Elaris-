# Component Health V0.4.2 — Technical Semantics Verification

**Estado:** `IMPLEMENTED_PENDING_LOCAL_VERIFICATION`  
**Baseline:** `component-health-v0.4.1-stable`  
**Rama:** `feat/component-health-technical-semantics-v042`  
**Clasificación de datos:** `SENSITIVE`  
**Exportación externa:** `NOT_APPROVED`

## Objetivo

V0.4.2 cierra la distancia entre "Elaris puede leer un campo" y "Elaris sabe qué significa técnicamente ese campo".

No agrega un health score, diagnóstico, probabilidad de falla, RUL, certificación ni decisión de retorno a servicio.

La salida de V0.4.2 usa cuatro estados explícitos:

- `CONFIRMED_NORMAL`
- `CONFIRMED_SUPPORTED`
- `CONFIRMED_UNSUPPORTED`
- `STILL_UNRESOLVED`

Un estado de verificación técnica describe el contrato de evidencia. No describe la salud del robot.

## Qué queda confirmado

### Mapping G1

La fuente pública oficial de Unitree fija:

- `RightWristYaw = 28`
- `LeftWristYaw = 21`
- `RightWristPitch = 27`
- `LeftWristPitch = 20`

Por lo tanto, el mapping del adaptador Elaris para OEM index 28 queda confirmado.

Esto no confirma que el mecanismo esté físicamente disponible en el robot concreto.

### Variantes 23-DOF / 29-DOF

Los ejemplos oficiales públicos de Unitree marcan wrist pitch/yaw como inválidos para G1 23-DOF.

Regla de V0.4.2:

- configuración explícita 23-DOF + fuente de configuración -> `CONFIRMED_UNSUPPORTED`;
- configuración explícita 29-DOF + telemetría usable -> `CONFIRMED_SUPPORTED`;
- configuración explícita 29-DOF + slot todavía sin telemetría física interpretable -> `STILL_UNRESOLVED`;
- configuración no demostrada -> `STILL_UNRESOLVED`.

No se permite inferir la variante únicamente porque un canal sea cero.

### MotorState HG

La declaración pública `MotorState_` confirma la existencia de:

- `q`
- `dq`
- `ddq`
- `tau_est`
- `temperature[2]`
- `vol`
- `motorstate`

Las helpers públicas de terminación G1 de Unitree confirman:

- `temperature[0]` -> motor casing temperature;
- `temperature[1]` -> motor winding temperature.

V0.4.2 mantiene separada esta confirmación de cualquier regla de ingeniería.

## Qué sigue sin resolverse

### Variante física del G1

El evidence contract actual no identifica de forma autoritativa 23-DOF versus 29-DOF.

Hasta cerrar esto, un wrist slot constante en cero no puede clasificarse como:

- sano;
- fallado;
- desconectado;
- no soportado.

Sigue siendo `STILL_UNRESOLVED`.

La próxima acción permitida es identificar la variante mediante evidencia de configuración de sólo lectura. No hace falta que Elaris envíe comandos de movimiento.

### Unidad / scaling de `vol`

El HG schema público confirma el campo `vol`, pero la declaración revisada no fija por sí sola el contrato de unidad/scaling que Elaris necesitaría para reglas de ingeniería.

Consecuencia: el valor puede preservarse como observación, pero no debe alimentar thresholds de pass/fail hasta cerrar el contrato OEM.

### `motorstate`

El HG schema confirma un `uint32 motorstate`.

V0.4.2 no encontró en las fuentes OEM públicas fijadas un enum/bitfield autoritativo para interpretar sus valores.

Consecuencia: Elaris conserva el número observado, pero no le asigna significado operativo.

### Timestamps duplicados

V0.3 ya protege coverage usando timestamps únicos. Los duplicados quedan contabilizados por separado.

Eso permite clasificar el comportamiento interno de Elaris como `CONFIRMED_NORMAL`, pero la causa de origen sigue abierta: DDS, batching, normalización o serialización.

### Phase end gap

Los límites humanos de fase y los límites observados de telemetría permanecen separados.

Cuando el último frame termina más de 2 segundos antes del final declarado, V0.4.2 mantiene `STILL_UNRESOLVED` hasta reconciliar:

- timing del operador;
- lifecycle de captura;
- último frame DDS observado.

## Criterio de cierre

V0.4.2 puede cerrarse como `VERIFIED_LOCAL` cuando:

1. TypeScript pasa.
2. El suite Component Health completo pasa.
3. Production build pasa.
4. E2E pasa con evidencia privada.
5. La vista Semantics mantiene el wrist como `STILL_UNRESOLVED` mientras no exista evidencia autoritativa de variante.
6. Ninguna pantalla o API convierte semántica técnica en health/safety conclusion.

La identificación de 23-DOF / 29-DOF es una investigación de campo posterior y no bloquea la integridad de V0.4.2; bloquea únicamente una clasificación más fuerte del wrist.
