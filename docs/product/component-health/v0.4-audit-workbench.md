# Component Health — Audit Workbench V0.4

**Estado:** `VERIFIED_LOCAL`  
**Aprobación para implementación:** Alexi Vion, 2026-10-07 («perfecto, sigamos» después de cerrar V0.3).  
**Base técnica:** Component Health V0.3 `VERIFIED_LOCAL`.  
**Branch:** `feat/component-health-audit-workbench-v04`.

## 1. Objetivo

V0.4 convierte el Evidence Engine reproducible de V0.3 en una experiencia operacional de análisis.

La condición central es:

> El Workbench no contiene números reales hardcodeados. Lee artefactos V0.3 privados en el servidor y deriva de ellos las pantallas de sesiones, componentes, fases, calidad y reporte interno.

La UI deja de necesitar editar archivos TypeScript cada vez que se genera una nueva auditoría.

## 2. Flujo

```text
Private V0.3 output pack
├── field-evidence-v03.json
├── field-evidence-v03.md
├── analysis-run.json
├── quality-v03.json
├── phase-manifest.json
└── checksums.sha256
              │
              ▼
       Workbench loader V0.4
       - server-side only
       - private path gate

       - schema V0.3 gate

       - duplicate-run reconciliation
              │
              ▼
        Audit Workbench UI
├── Overview
├── Sessions / Analysis Runs
├── Components
├── Phase Explorer
├── Quality Review
└── Internal Draft Report
```

## 3. Fuente privada

Por defecto el servidor explora:

```text
$HOME/elaris-private
```

buscando `field-evidence-v03.json` en profundidad acotada.

Opcionalmente:

```bash
export ELARIS_COMPONENT_HEALTH_V03_REPORT=/absolute/private/path/field-evidence-v03.json
```

o:

```bash
export ELARIS_COMPONENT_HEALTH_V03_ROOT=/absolute/private/catalogue/root
```

Si existen varias ejecuciones únicas:

```bash
export ELARIS_COMPONENT_HEALTH_ACTIVE_ANALYSIS_ID=CH-A03-...
```

Sin esa variable, se activa el artefacto privado modificado más recientemente y la UI muestra una advertencia.

## 4. Integridad y seguridad

**Network boundary:** V0.4 es un Workbench **local**. Para revisar material SENSITIVE debe ejecutarse vinculado a `127.0.0.1`, no `0.0.0.0`, y nunca exponerse en Internet sin autenticación, aislamiento por organización y autorización de datos. En `NODE_ENV=production` la carga de evidencia privada queda desactivada salvo opt-in explícito `ELARIS_COMPONENT_HEALTH_ALLOW_PRODUCTION_PRIVATE_EVIDENCE=1`; dicho opt-in **no** constituye autenticación ni aprobación de exportación.

**Browser boundary:** el navegador recibe **agregados derivados clasificados SENSITIVE** para permitir la UI interactiva. Lo que se mantiene exclusivamente en el servidor son rutas privadas, registries/verified-file lists, ciphertext, claves y raw telemetry. Por ello la UI debe usarse sólo en un entorno privado/autorizado.

Antes de parsear un reporte, V0.4 exige el `checksums.sha256` generado por V0.3 y verifica:

- `field-evidence-v03.json`;
- `field-evidence-v03.md`;
- `analysis-run.json`;
- `quality-v03.json`;
- `phase-manifest.json`.

El Workbench falla cerrado si:
- cambia un archivo después del sellado;
- falta un archivo requerido en el registry;
- el checksum no coincide;
- el schema no es `0.3.0`;
- la evidencia no es `OBSERVED`;
- el artifact no conserva `SENSITIVE`;
- la referencia no es `SAME_SESSION_IDLE_PRIMARY`;
- una fase no contiene 29 slots;
- dos artifacts con el mismo `analysisId` tienen bytes distintos;
- el report está dentro del Git working tree;
- se intenta cargar explícitamente un symlink.

El navegador **no** recibe:
- paths privados;
- registry hashes completos;
- verified-file lists;
- ciphertext;
- passphrases;
- raw telemetry.

La UI muestra sólo IDs y fingerprints truncados cuando son útiles para revisión.

## 5. Pantallas

### Overview

Muestra:
- cantidad de AnalysisRuns privados detectados;
- fases;
- slots;
- warnings de QA;
- active AnalysisRun;
- reference policy;
- clasificación/export boundary;
- cobertura por fase;
- grupos de quality findings.

### Sessions / Analysis Runs

Lista artifacts únicos por `analysisId`.

Dos copias con igual `analysisId` + igual report SHA-256 se deduplican y se registra el número de copias privadas. Dos copias con el mismo ID pero bytes distintos producen error.

El detalle de sesión muestra la procedencia de observed y historical baseline sin revelar hashes privados.

### Components

La tabla se deriva del catálogo de 29 slots del artifact activo.

Para cada componente se calculan:
- fases observadas;
- fases faltantes;
- unresolved si alguna fase conserva `OBSERVED_UNRESOLVED_SLOT`;
- acceso al detalle por slug estable.

### Component detail

Muestra por las 8 fases:
- availability / slot status;
- position range;
- velocity absP95;
- torque absP95;
- torque coverage;
- ratio contra same-session idle cuando existe.

También muestra semantic status de cada señal y QA records agrupados del componente.

### Phase Explorer

Renderiza la matriz completa del artifact:
- 29 slots;
- todas las fases;
- torque absP95 idle → observed;
- ratio;
- coverage;
- cross-phase matrix.

No usa `lib/demo/component-health-field-data.ts`.

### Quality Review

Agrupa los records de V0.3 por:
- severidad;
- code;
- fases;
- componentes;
- señales.

Los 1615 records del Dataset #002 se presentan como QA/semantics evidence, **no** como fallos del robot.

### Internal Draft Report

Genera una vista interna a partir del artifact activo:
- boundaries;
- provenance resumida;
- phase overview;
- top torque fingerprints;
- quality summary.

Siempre se etiqueta `DRAFT · NOT APPROVED FOR EXPORT`.

## 6. Legacy

La antigua URL:

```text
/platform/component-health/reports/field-evidence
```

redirige al nuevo draft V0.4.

Las rutas sintéticas retiradas en V0.2.1 continúan redirigidas y no vuelven a aparecer como evidencia real.

Las páginas antiguas de robot permanecen fuera de la navegación V0.4 hasta que exista una identidad/persistencia de robot validada para Workbench.

## 7. Persistencia

Este primer V0.4 es **artifact-backed y read-only**.

No copia raw telemetry a SQLite y no crea todavía un modelo permanente de sesiones/notes. Esto es intencional: primero se valida que el operador pueda inspeccionar una auditoría completa desde artifacts V0.3 sin hardcoding.

Persistencia de review notes / audit status sólo se incorpora después de validar este flujo, evitando fijar prematuramente entidades que todavía no demostraron trabajo repetido.

## 8. Gates

Antes de `VERIFIED_LOCAL`:

```bash
pnpm typecheck
pnpm test:component-health
pnpm build
pnpm exec playwright test tests/e2e/component-health.spec.ts --reporter=line
```

Con Dataset #002 real disponible en `$HOME/elaris-private`, comprobar manualmente:

- Overview muestra `REAL V0.3 ARTIFACT · V0.4`;
- Sessions deduplica run A / run B al mismo Analysis ID;
- Components muestra 29 slots;
- Left hip pitch navega a evidencia de las 8 fases;
- Phase Explorer usa datos del artifact y no el fixture V0.2;
- Quality Review agrupa los QA records;
- Draft Report dice `NOT APPROVED FOR EXPORT`;
- ninguna pantalla revela private paths, registry hashes completos o passphrases;
- antiguas rutas sintéticas siguen redirigidas.

Si no existe evidencia privada, el Workbench debe mostrar un empty state seguro y no caer en datos hardcodeados.

### Conclusión

El alcance **artifact-backed/read-only** definido para V0.4 cumple su Definition of Done y pasa a `VERIFIED_LOCAL`.

Esto **no** significa:
- owner approval;
- aprobación de exportación;
- release público;
- autenticación/multi-tenant;
- persistencia de review notes;
- señal seleccionable completa en Phase Explorer;
- diagnóstico, health score, failure probability o RUL.

Los puntos de persistencia/notas y expansión del Phase Explorer pasan a backlog posterior y no deben reinterpretarse como funcionalidades verificadas en V0.4.

## 10. Fuera de alcance

- edición de phases desde UI;
- review notes persistentes;
- approval workflow;
- export a cliente;
- multi-user/multi-tenant;
- cloud upload;
- health/anomaly/failure scores;
- diagnóstico;
- RUL;
- control del robot;
- raw telemetry charts;
- segundo OEM.

## 11. Definition of Done

V0.4 pasa a `VERIFIED_LOCAL` cuando:

1. typecheck/tests/build/E2E son verdes;
2. el Dataset #002 privado aparece automáticamente sin editar TypeScript;
3. run A/B se deduplican como un AnalysisRun;
4. los 29×8 datos reales son navegables;
5. Quality Review agrupa records sin claims de health/failure;
6. Draft Report mantiene límites y export `NOT_APPROVED`;
7. checksum tampering falla cerrado;
8. no existe evidencia real hardcodeada en las rutas activas V0.4;
9. no se expone filesystem privado al browser;
10. el registro de versiones se actualiza con evidencia de operador.
