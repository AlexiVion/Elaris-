# Component Health V0.4.3 — Offline Robustness & Field Instrumentation

**Estado:** `IMPLEMENTED_PENDING_LOCAL_VERIFICATION`  
**Baseline:** `release/component-health-v0.4.2`  
**Rama:** `feat/component-health-offline-instrumentation-v043`  
**Clasificación de datos:** `SENSITIVE`  
**Modo de robot:** `READ_ONLY`

## Contexto

V0.4.2 cerró la semántica técnica que podía resolverse sin nueva evidencia física. Quedan tres preguntas abiertas:

1. por qué `RightWristYaw / OEM index 28` no produjo telemetría física interpretable en la captura existente;
2. dónde se originan los timestamps duplicados;
3. por qué el último frame observado puede terminar antes del fin humano declarado de una fase.

Actualmente no hay acceso al robot y no puede ejecutarse una nueva sesión. V0.4.3 avanza únicamente sobre software, replay e instrumentación para que la próxima sesión sea discriminante.

## Objetivo

Convertir preguntas ambiguas de campo en evidencia atribuible.

V0.4.3 NO resuelve la condición física del wrist sin robot. Prepara el pipeline para distinguir:

- callback SDK;
- sampling del bridge;
- recepción Node;
- normalización;
- persistencia;
- lifecycle de captura;
- source tick OEM;
- movimiento dinámico observado de un componente.

## Cambios implementados

### Provenance de frame

El contrato de transporte acepta metadata opcional:

- `bridgeObservedAtUnixNs`;
- `bridgeObservedMonotonicNs`;
- `callbackSequence`;
- `emittedSequence`;
- `receivedAt`.

Los nanosegundos de Unix se mantienen como strings para evitar pérdida de precisión en JavaScript.

El bridge Unitree añade contadores independientes de callback y emisión. El rate limit se apoya en reloj monotónico.

### Provenance persistida

Los raw frames pueden retener:

- metadata del bridge;
- `receivedAt`;
- `normalizedAt`;
- `persistedAt`;
- `sourceTick`.

La evidencia sigue cifrada localmente.

### Lifecycle de captura

El manifest puede registrar:

- `collectorStartedAt`;
- `transportReadyAt`;
- `captureRequestedStartAt`;
- `firstFrameAt`;
- `lastFrameAt`;
- `captureRequestedEndAt`;
- `unsubscribeRequestedAt`;
- `unsubscribeCompletedAt`;
- `finalizeStartedAt`;
- `finalizedAt`.

Esto permite separar un gap real de telemetría de una diferencia entre timing del operador y lifecycle del collector.

### Capture diagnostics

Nuevo analizador descriptivo `capture-diagnostics-v043`.

Detecta:

- timestamps de captura duplicados;
- source ticks duplicados;
- emitted sequences duplicados;
- regresiones de callback/emisión;
- gaps de emitted sequence;
- distancia entre último frame y fin solicitado.

Salida:

`DESCRIPTIVE_PIPELINE_DIAGNOSTICS_ONLY`

No diagnostica robot ni hardware.

Nuevo comando:

```bash
pnpm edge diagnose-capture <capture-dir>
```

Requiere `ELARIS_EDGE_PASSPHRASE`.

### Component probe

Nuevo analizador `component-probe-v043`.

Clasificaciones:

- `DYNAMIC_SIGNAL_OBSERVED`
- `STATIC_OR_ZERO_SIGNAL`
- `NOT_OBSERVED`

Siempre conserva:

`NO_HEALTH_OR_SAFETY_CONCLUSION`

El probe considera movimiento observable en señales físicas normalizadas y conserva `mode_machine` como contexto.

Comando preparado:

```bash
pnpm edge probe-unitree-component \
  --interface enp0s8 \
  --component right-wrist-yaw \
  --duration 30 \
  --hz 20
```

El comando sólo subscribe `rt/lowstate`. No envía comandos al robot.

### Replay determinista

Escenarios incorporados:

- `G1_23_DOF`;
- `G1_29_DOF_WRIST_STATIC`;
- `G1_29_DOF_WRIST_MOVING`;
- `DUPLICATE_CAPTURE_TIMESTAMP`.

Permiten desarrollar y verificar el pipeline sin hardware.

## Boundaries

V0.4.3 no produce:

- HEALTHY / FAILED;
- SAFE;
- CERTIFIED;
- READY FOR SERVICE;
- causa física confirmada del slot 28;
- causa de DDS confirmada sin captura instrumentada;
- control remoto;
- actuation.

## Blockers explícitos

### Bloqueado por acceso físico

- observación del wrist durante movimiento real;
- nueva captura instrumentada;
- discriminación definitiva de slot 28;
- atribución empírica de los duplicados de la sesión futura.

### No bloqueado

- provenance de software;
- replay;
- diagnostics;
- tests;
- protocolo de campo;
- preparación del probe.

## Gate de V0.4.3

Antes de declarar `VERIFIED_LOCAL`:

```bash
pnpm typecheck
pnpm test:component-health
pnpm build
```

No requiere migración de base de datos.

## Criterio de salida

Cuando el gate local pase, V0.4.3 queda `READY_FOR_FIELD`.

`READY_FOR_FIELD` significa que el software está preparado para la próxima sesión. No significa que los blockers físicos estén resueltos.
