# Component Health — Evidence Engine V0.3

**Estado:** `IMPLEMENTED_PENDING_VERIFICATION`  
**Aprobación para implementación:** Alexi Vion, 2026-10-07 (alcance técnico V0.3; no aprobación de release ni de export de datos).  
**Base:** V0.2.1 `VERIFIED_LOCAL`.  
**Branch:** `feat/component-health-evidence-engine-v03`.

## 1. Objetivo

V0.3 elimina la divergencia principal entre el analyzer técnico y la demo: la referencia primaria deja de ser el baseline histórico para pasar a ser una fase **`IDLE_BASELINE` de la misma sesión**, humana y explícitamente confirmada.

El baseline histórico sigue existiendo como contexto secundario y mantiene su propia cadena de procedencia.

V0.3 genera un artefacto reproducible e independiente de la UI:

```text
source / working copies
        ↓
integrity + lineage
        ↓
Field Evidence V0.2.1 analyzer
        ↓
same-session IDLE_BASELINE
        ↓
29 slots × N phases
        ↓
quality + semantics + comparisons
        ↓
AnalysisRun / JSON / Markdown / checksums
```

## 2. Contrato de evidencia

El resultado `field-evidence-v03.json` contiene:

- `schemaVersion=0.3.0`;
- `analysisId` determinista;
- `inputFingerprint` determinista;
- lineage separada para:
  - sesión observada original/copia de trabajo;
  - baseline histórico original/copia de trabajo;
- `phaseManifestSha256`;
- referencia primaria `SAME_SESSION_PHASE / IDLE_BASELINE`;
- baseline histórico marcado `SECONDARY_CONTEXT_ONLY`;
- las 29 posiciones OEM del catálogo G1 en cada fase;
- ausencia representada como `MISSING/null`, nunca como cero fabricado;
- resumen de señales por componente/fase;
- comparaciones contra idle de la misma sesión;
- state codes nuevos respecto de idle;
- fingerprints completos ordenados por torque absP95 ratio;
- ventanas declaradas y efectivamente observadas;
- findings de calidad;
- status explícito de semánticas OEM no confirmadas;
- límites de interpretación.

## 3. Reproducibilidad

El engine no introduce timestamps de ejecución en el objeto principal.

El `analysisId` e `inputFingerprint` dependen de:
- versión del engine;
- hash canónico del phase manifest;
- hashes de los registries de source/working copy;
- identities de sesiones;
- política de referencia.

Con entradas iguales, el objeto de evidencia V0.3 debe ser idéntico.

El CLI escribe:
- `field-evidence-v03.json`;
- `field-evidence-v03.md`;
- `analysis-run.json`;
- `quality-v03.json`;
- `phase-manifest.json`;
- `checksums.sha256`.

Los artefactos siguen siendo **SENSITIVE** mientras el owner no autorice explícitamente exportación.

## 4. Política de referencia

### Primaria

`IDLE_BASELINE` de Dataset #002 / de la misma sesión analizada.

Motivo: comparte robot, captura, configuración temporal y contexto mucho mejor que el baseline histórico.

### Secundaria

Dataset #001 / historical baseline.

Se conserva para:
- identidad;
- contexto histórico;
- comparación exploratoria separada;
- continuidad de evidencia.

No se usa como prueba de degradación, fallo o desgaste.

## 5. 29 × fases

El V0.3 materializa cada slot del catálogo Unitree G1 por fase.

```text
slot observado → OBSERVED + summaries
slot ausente    → MISSING + null
slot ambiguo    → OBSERVED_UNRESOLVED_SLOT
```

Un slot faltante jamás se representa como señal física cero.

## 6. Data quality

Controles implementados:
- coverage basada en timestamps únicos;
- fail-closed si una coverage supera 100%;
- ventana observada separada de ventana declarada;
- warning si inicio/fin observados difieren >2 s de la declaración;
- missing slots por fase;
- low coverage <95%;
- conteos de timestamps de señal duplicados sin inflar coverage;
- máximo/mediana de intervalos entre frames observados y aviso de gaps grandes en relación con su cadencia;
- constant-zero reportado como información, no diagnóstico;
- unresolved slot explícito;
- semánticas OEM sin validación marcadas como no confirmadas.

## 7. Semánticas

| Señal | Estado V0.3 |

| joint.position | `NORMALIZED_OBSERVATION` |
| joint.velocity | `NORMALIZED_OBSERVATION` |
| joint.torque_estimate | `NORMALIZED_ESTIMATE` |
| motor.voltage | `OEM_SEMANTICS_UNCONFIRMED` |
| motor.temperature.casing | `OEM_SEMANTICS_UNCONFIRMED` |
| motor.temperature.winding | `OEM_SEMANTICS_UNCONFIRMED` |

«Normalized» indica preservación/traducción de la señal OEM, no calibración ni aprobación del significado físico completo.

## 8. Uso CLI

### Original observado + baseline original

```bash
pnpm edge health-report-v03 <baseline-original> <observed-original> \
  --phases <phase-manifest.json> \
  --salvage-hashes <observed-salvage.sha256> \
  --out <private-output>
```

### Dataset actual con ambas working copies recifradas

```bash
pnpm edge health-report-v03 <baseline-rekeyed> <observed-rekeyed> \
  --phases <phase-manifest.json> \
  --source-dir <observed-original> \
  --source-salvage-hashes <observed-source-sha256.txt> \
  --derivative-hashes <observed-rekey-sha256.txt> \
  --baseline-source-dir <baseline-original> \
  --baseline-source-hashes <baseline-source-checksums.sha256> \
  --baseline-derivative-hashes <baseline-rekey-sha256.txt> \
  --out <private-output>
```

`ELARIS_EDGE_PASSPHRASE` se toma exclusivamente del entorno.

**Límite de implementación actual:** la lectura de archivos cifrados es secuencial, pero el cálculo exacto de percentiles conserva arrays de muestras en memoria. V0.3 debe medir RAM/CPU con Dataset #002 y registrar el resultado; procesamiento *bounded-memory* queda como optimización posterior si el benchmark demuestra necesidad.

Esos alcances pertenecen a V0.4+ o a investigación posterior.

1. typecheck/tests/build pasan;
2. Dataset #002 corre 2× y outputs deterministas coinciden;

4. el output 29×8 no fabrica datos ausentes;
5. same-session idle gobierna comparisons;
6. quality findings y semantics están explícitas;
7. ningún artefacto SENSITIVE se agrega a Git;
8. el registro de versiones se actualiza con la evidencia real.
