# Component Health — V0.4.1 Human Review & Persistence

**Estado:** `VERIFIED_LOCAL`  
**Aprobación para implementación:** Alexi Vion, 2026-10-07.  
**Base:** V0.4 Audit Workbench `VERIFIED_LOCAL`.  
**Branch:** `feat/component-health-review-persistence-v041`.

## 1. Problema real

V0.4 permite ver la evidencia, pero todavía obliga al operador a entender demasiados detalles técnicos.

El objetivo de V0.4.1 no es inventar un diagnóstico automático. Es convertir los findings de calidad en una cola corta de preguntas accionables y guardar el estado de esa revisión.

El principio es:

> El operador no debe decidir si el robot está sano. Debe poder ver qué sabemos, qué no sabemos y qué necesita una revisión técnica/OEM antes de elevar un claim.

## 2. Qué agrega

- Página `/platform/component-health/review`.
- Cola derivada automáticamente de los grupos QA V0.3.
- Explicación en lenguaje simple.
- Acción recomendada por tipo de finding.
- Prioridad HIGH / MEDIUM / LOW.
- Estado persistente por AnalysisRun.
- Disposición persistente por grupo de calidad.
- Nota general y notas por item.
- Timestamps de persistencia.
- SQLite local mediante Prisma.
- API local para guardar revisión.
- V0.4.1 no cambia `NOT_APPROVED` de export.

## 3. Estados permitidos

### Review

- `AWAITING_TECHNICAL_REVIEW`
- `IN_REVIEW`
- `REVIEWED_FOR_COMPLETENESS`
- `BLOCKED`

`REVIEWED_FOR_COMPLETENESS` significa que se revisó la completitud documental de la evidencia y sus límites.

**No significa:**
- healthy;
- safe;
- certified;
- approved for export;
- failure-free.

### Review item

- `OPEN`
- `ACKNOWLEDGED`
- `NEEDS_FOLLOWUP`
- `DATA_LIMITATION`

## 4. Traducción automática de findings a acciones

| Finding | Prioridad | Acción |
|---|---|---|
| UNRESOLVED_COMPONENT_SLOT | HIGH | Verificar mapping / disponibilidad real del slot OEM |
| PHASE_NO_OBSERVED_TELEMETRY | HIGH | Repetir o recuperar capture |
| MISSING_COMPONENT_SLOTS | HIGH | Confirmar omisión y repetir si no fue intencional |
| PHASE_OBSERVATION_ENDS_BEFORE_DECLARED_END | MEDIUM | Reconciliar boundary humano vs telemetry |
| PHASE_OBSERVATION_STARTS_AFTER_DECLARED_START | MEDIUM | Reconciliar inicio |
| OEM_SEMANTICS_UNCONFIRMED | MEDIUM | Validar units / state codes con fuente OEM |
| DUPLICATE_SIGNAL_TIMESTAMP | MEDIUM | Entender origen y preservar regla de dedupe |
| TELEMETRY_FRAME_GAP | MEDIUM | Revisar continuidad de capture |
| LOW_SIGNAL_COVERAGE | MEDIUM | Revisar missingness |
| CONSTANT_ZERO_SIGNAL | LOW | Clasificar cero real vs unsupported/unavailable |

## 5. Persistencia mínima

Dos entidades nuevas:

```text
ComponentHealthReview
└── ComponentHealthReviewItem[]
```

No se persiste raw telemetry ni se copia el artifact V0.3 a SQLite.

La identidad de la evidencia continúa siendo `analysisId`.

## 6. Seguridad y claims

V0.4.1 no agrega ningún botón de aprobación de datos o release externo.

El review state es un workflow local.

La UI continúa mostrando:
- `SENSITIVE`;
- `NOT APPROVED`;
- límites de interpretación.

No se transforma un finding de calidad en un fallo de componente.

## 7. Migración local

Aplicar sin resetear la DB:

```bash
pnpm exec prisma migrate deploy
pnpm exec prisma generate
```

No usar `db:reset`.

## 8. Gates

```bash
pnpm exec prisma migrate deploy
pnpm exec prisma generate
pnpm typecheck
pnpm test:component-health
pnpm build
pnpm exec playwright test tests/e2e/component-health.spec.ts --reporter=line
```

Después verificar:
1. Review abre con el AnalysisRun real.
2. La cola muestra grupos accionables, no 1615 filas crudas.
3. Guardar estado y nota persiste tras refresh.
4. Guardar disposición de un item persiste tras refresh.
5. `REVIEWED_FOR_COMPLETENESS` no cambia export status.
6. Draft Report continúa `NOT APPROVED FOR EXPORT`.
