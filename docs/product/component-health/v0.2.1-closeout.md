- Los captures FINALIZED pasan una verificación explícita de su `checksums.sha256` antes de usarse como sesión observada en `health-report`.

## 2. Comandos de análisis — dos modos, no intercambiables

### Captura original OPEN analizada directamente

```bash
pnpm edge health-report <baseline-dir> <original-open-dir> \
  --phases <phase-manifest.json> \
  --salvage-hashes <source-salvage-sha256.txt> \
  --out <direct-output-dir>
```

Los hashes de origen se validan **contra los bytes del directorio original**.

### Captura OPEN analizada desde una copia recifrada

```bash
pnpm edge health-report <baseline-working-dir> <rekeyed-observed-dir> \
  --phases <phase-manifest.json> \
  --source-dir <original-open-dir> \
  --source-salvage-hashes <original-salvage-sha256.txt> \
  --derivative-hashes <rekeyed-checksums.sha256> \
  --out <new-report-dir>
```

Los tres flags de procedencia son obligatorios juntos. No usar `--salvage-hashes` con un registro de hashes de la derivada: eso confunde la verificación del origen con la de la copia.

**Importante:** los registros SHA-256 prueban coincidencia con bytes registrados, no autenticidad del autor, identidad semántica del contenido ni equivalencia del plaintext. El baseline histórico también requiere trazabilidad origen→derivada independiente antes de aprobar un paquete externo completo.

## 5. Significado de cierre

- `IMPLEMENTADA`: código subido y PR abierto.
- `VERIFICADA`: checks automáticos y recorrido manual con evidencia registrada.
- `APROBADA`: firma humana explícita sobre alcance/limitaciones.
- `PUBLICABLE`: aprobación específica de datos y seguridad, independiente de que el código funcione.

**Nunca** pasar automáticamente de `VERIFICADA` a `APROBADA` o `PUBLICABLE`.
