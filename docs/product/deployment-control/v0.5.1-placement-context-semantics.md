# Deployment Control V0.5.1 — Placement Context Semantics

**Status:** `PLANNED / READY_FOR_IMPLEMENTATION_AFTER_PORTFOLIO_REVIEW`  
**Parent scope:** V0.5 Real Institutional Placement Reconciliation  
**Selected case:** `DC-CASE-S21-HMND-001`

## 1. Problem discovered by the real case

The current domain was optimized for a commercial/operational deployment:

```text
Customer → Site → Deployment → Task
```

The Siglo 21 / Humandroid case is different:

```text
Humandroid robot
        ↓
hosted at Universidad Siglo 21
        ↓
institutional agreement
        ↓
no specific production task
        ↓
no commercial customer relationship inferred
```

Current schema cannot encode that without fiction.

## 2. Existing assumptions affected

### Prisma

- `Site.customerId` is required.
- `Deployment.customerId` is required.
- `Deployment.taskId` is required.
- `Deployment.lifecycle` only supports TEST/PILOT/LIMITED/PRODUCTION semantics.
- `operatingMode` and `humanExposure` are required even when no operational assignment exists.
- `Baseline.taskSnapshot` is required.

### Query / UI / Reports

- Deployment summary exposes `customerName`.
- Deployment table labels a mandatory Customer column.
- Home renders `customerName · city, country`.
- System Passport assumes every deployment has a customer.
- Deployment Readiness Pack assumes `customer`, `task`, operating mode and human exposure always exist.
- Several labels/copy assume deployment means commercial operational use.

### Readiness

The readiness engine already behaves correctly for optional categories:
- a category with no required evidence/approval is `NOT_REQUESTED`;
- it does not lower the readiness percentage.

Therefore V0.5.1 should **not** redesign readiness merely because Siglo 21 has no customer/insurance requirements.

System Identity may remain REVIEW_REQUIRED when identity facts such as serial are unknown. That is desirable.

## 3. Recommended minimal domain change

### Principle

Do not delete the commercial model. Make it an optional layer over a more general placement context.

### Organization

Reuse `Organization` for real counterparties/institutions.

Expected case:
- Humandroid → provider/owner context.
- Universidad Siglo 21 → host organization.

### Site

Recommended direction:

```text
Site
├── hostOrganizationId?    NEW
├── customerId?            OPTIONAL legacy/commercial link
├── name
├── city
├── country
└── environmentType
```

A site may be an institutional host without being a commercial customer site.

### Deployment

Recommended direction:

```text
Deployment
├── code
├── name
├── contextKind            NEW
├── providerOrganizationId? NEW
├── hostOrganizationId?    NEW or derivable via Site
├── customerId?            OPTIONAL
├── siteId                 REQUIRED when physically placed
├── taskId?                OPTIONAL
├── lifecycle?             OPTIONAL / retained for operational maturity
├── operationalState
├── operatingMode?         OPTIONAL
├── humanExposure?         OPTIONAL
├── description
└── activeBaselineId?
```

### Context kind

Candidate values:

```text
INSTITUTIONAL_PLACEMENT
INTERNAL_LAB
TEST
PILOT
DEMO
PRODUCTION
```

This list is provisional. The implementation PR may narrow it, but must represent the selected real case without classifying it as PILOT/PRODUCTION.

### Baseline

`Baseline.taskSnapshot` should become optional or explicitly support no assigned task.

Recommended:
- `taskSnapshot: String?`
- preserve `environmentSnapshot` as frozen context.
- add provider/host/contextKind to the frozen environment/context snapshot.

A baseline means **reference state at a time**, not acceptance.

## 4. Why not simply create a fake Customer + Task?

Because that would corrupt shared Elaris truth.

Downstream products could then infer:
- customer requirements;
- customer approval;
- operational task;
- production readiness;
- insurance context;

from records that never existed.

The real case is valuable precisely because it prevents this semantic shortcut.

## 5. Compatibility requirements

V0.5.1 must preserve the existing commercial golden scenario.

After migration both cases must coexist:

### Existing commercial case

```text
Customer
→ customer site
→ task
→ pilot/production-style deployment
→ readiness/evidence/approval
```

### New institutional placement case

```text
provider organization
→ host organization/site
→ institutional placement
→ optional/no task
→ technical baseline/evidence
→ no implied customer approval/readiness
```

## 6. Query/UI adaptation

### Lists

Replace unconditional Customer display with context-aware counterpart:

Examples:

```text
Northgas Energy
Bergen, Norway
Pilot
```

and

```text
Universidad Siglo 21
Córdoba, Argentina
Institutional placement
```

Do not show an empty “Customer” field as if data were missing when customer is not applicable.

### Deployment detail

Separate:

- Provider / owner context
- Host organization
- Site
- Commercial customer, if applicable
- Assigned task, if applicable
- Context kind
- Operational state
- Operating mode, if applicable
- Human exposure, if applicable

### Reports

System Passport and Deployment Record must use nullable/conditional commercial/task fields.

No report for Siglo 21 may contain:
- fictional customer;
- fictional task;
- customer approval;
- production readiness language.

## 7. Deterministic/readiness behavior

Keep the current readiness principle:

```text
required + applicable
```

Only evidence/approvals explicitly required for this placement enter the denominator.

Categories with nothing requested remain `NOT_REQUESTED`.

Do not create special “easy readiness” for institutional placements. Unknown identity/configuration should still surface honestly.

## 8. Migration strategy

Recommended implementation order:

1. add new nullable organization/context fields;
2. make commercial/task-only relations nullable;
3. backfill existing seed/demo deployments with a commercial context kind;
4. update TS enums/Zod/copy labels;
5. update query adapters and reports;
6. add institutional-placement seed/fixture based on the real case but with only approved/public-safe facts;
7. add migration tests;
8. keep sensitive telemetry outside DB/repo and link only authorized metadata/evidence refs.

No destructive reset of real private evidence is required.

## 9. Required tests

### Domain / DB

- commercial deployment still round-trips;
- institutional placement persists with `customerId = null`;
- institutional placement persists with `taskId = null`;
- site can belong to host organization without customer;
- baseline can exist without task snapshot;
- historical baseline hash/config semantics remain deterministic.

### Metrics

- no CUSTOMER_REQUIREMENTS/INSURANCE items → `NOT_REQUESTED`;
- those categories do not penalize readiness;
- missing serial/identity remains visible as REVIEW_REQUIRED.

### Reports

- System Passport renders institutional placement without customer.
- Deployment Record/Readiness Pack conditionally omits non-applicable task/customer fields.
- no string such as “customer approved” is generated for the selected case.

### Existing regression

- golden Deployment Control diff/impact tests remain unchanged and green;
- existing seeded commercial deployment still renders.

## 10. Acceptance gate

V0.5.1 is `VERIFIED_LOCAL` only when:

- migration passes;
- existing commercial scenario passes;
- institutional placement fixture passes;
- typecheck/tests/build/E2E pass;
- UI/report copy distinguishes host/provider/customer/task correctly;
- no fake fact is required to render the selected real case.
